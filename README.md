# CarCarePrototype

Диагностический Android-прототип для исследования автомобильных данных через **Android Auto** и **Bluetooth**. Приложение показывает ответы API, состояния подключения и разрешений, сохраняет события и позволяет экспортировать их для анализа.

Прототип служит техническим стендом для будущего **CarCare** — помощника по обслуживанию автомобиля. Основное приложение создаётся отдельным проектом. В этом репозитории исследуются источники данных и надёжность интеграций; гараж, расчёт ТО и сервисная история здесь пока не реализованы.

## Зачем нужен проект

Прежде чем использовать автомобильные показания в рекомендациях по ТО, нужно понять, какие данные действительно доступны, что они означают и как ведут себя при переподключении, отказе в разрешениях или отсутствии ответа.

CarCarePrototype помогает воспроизводить такие ситуации, сохранять наблюдения и отделять полученное число от подтверждённого общего пробега автомобиля. Диагностика в этом проекте относится к работе интеграций, а не к поиску неисправностей машины.

## Что уже умеет

### Android Auto

- Открывать диагностический экран на телефоне и автомобильный экран через AndroidX Car App Library.
- Отслеживать жизненный цикл автомобильной сессии и состояние доступа к показаниям пробега.
- Подписываться на `CarInfo` mileage API, показывать сырой ответ, его статус и время получения.
- Различать текущую попытку запроса, последний ответ API и последнее допустимое числовое показание.
- Показывать отсутствие ответа, таймаут, недоступные данные и отказ в разрешении; повторять запрос по команде пользователя.
- Отбрасывать устаревшие callbacks и не переносить показание в новое подключение или под другую метку автомобиля.
- Задавать ручную метку `Car ID` для группировки диагностических журналов.

Все показания имеют статус **`UNVERIFIED`**. Успешный ответ API сам по себе не подтверждает, что число является общим одометром конкретного автомобиля. Его нужно сопоставлять с приборной панелью и проверять в контексте используемого оборудования.

### Bluetooth

- Показывать состояние адаптера и список сопряжённых устройств.
- Искать устройства через Bluetooth Classic и BLE.
- Отображать имя, адрес, тип устройства, доступный RSSI и UUID сервисов.
- Запрашивать SDP и расшифровывать известные Classic/GATT UUID по встроенным справочникам.
- Подключаться по SPP/RFCOMM к подходящему сопряжённому устройству и журналировать поступающие байты.
- Исследовать список GATT-сервисов, характеристик и их свойств у BLE-устройства.
- Показывать стадии соединения, ошибки и таймауты; завершать активные операции при остановке экрана.

Bluetooth-часть исследует доступные транспорты и сервисы. Декодер OBD/ELM327, автомобильные команды и универсальное получение пробега через Bluetooth в ней не реализованы.

### Журналы и экспорт

- Сохранять диагностические события локально в формате **JSONL** — одна JSON-запись на строку.
- Восстанавливать автомобильный журнал после перезапуска и показывать последние 100 событий на вкладке Android Auto телефона.
- Экспортировать весь автомобильный журнал или последнюю сессию в папку, выбранную системным диалогом Android.
- При совпадении имени файла предлагать дописать данные, заменить файл или выбрать другое имя.
- Вести отдельную Bluetooth-историю с экспортом и ручной очисткой.

Журналы могут содержать введённую метку автомобиля, имена и адреса Bluetooth-устройств. Экспорт предназначен для осознанной передачи диагностических данных; автоматическая отправка на сервер в прототипе не реализована.

## Как устроено

В проекте один Gradle-модуль `:app`. Интерфейс телефона написан на Jetpack Compose и содержит две вкладки: **Android Auto** и **Bluetooth**.

На телефоне действия идут из Compose в ViewModel, затем в контракты диагностических сервисов. Репозитории владеют состоянием и операциями, платформенные адаптеры работают с Android API, а интерфейс наблюдает за состоянием через `StateFlow` с учётом жизненного цикла.

Автомобильный путь начинается с `CarAppService` и `CarSession`. Подпиской на показания управляет `MileageSubscription`; границы подключения и выбранной метки проверяются перед применением обновления. Автомобильный журнал обрабатывается последовательно и доступен сервису даже без открытой Activity телефона.

| Каталог исходников | Ответственность |
|---|---|
| [`car/`](app/src/main/java/com/example/carcareprototype/car/) | Автомобильная сессия и экран, подписка на показания, модель пробега, хранение и экспорт автомобильных записей |
| [`diagnostics/`](app/src/main/java/com/example/carcareprototype/diagnostics/) | Общий диагностический журнал, состояние и сервис операций экспорта |
| [`presentation/`](app/src/main/java/com/example/carcareprototype/presentation/) | Телефонный экран Android Auto, ViewModel и диалоги экспорта |
| [`bluetooth/`](app/src/main/java/com/example/carcareprototype/bluetooth/) | Classic/BLE, SDP, GATT, RFCOMM, состояние устройств и Bluetooth-история |
| [`ui/theme/`](app/src/main/java/com/example/carcareprototype/ui/theme/) | Тема Compose |

Требования к ответственности компонентов, владению состоянием и последнему рефакторингу описаны в [ARCHITECTURE.md](https://github.com/XataBq/CarCarePrototype/blob/master/ARCHITECTURE.md).

Совместимость исходников с Java 11 не означает, что Gradle следует запускать на JDK 11.

## Сборка и запуск

Понадобятся Android Studio с поддержкой указанного AGP, Android SDK для выбранного compile SDK и настроенный доступ к JDK/toolchain 21. Android Studio может создать локальный `local.properties` с путём к SDK; этот файл не нужно добавлять в репозиторий.

Команды для PowerShell:

```powershell
git clone https://github.com/XataBq/CarCarePrototype.git
Set-Location -LiteralPath '.\CarCarePrototype'
.\gradlew.bat --version
.\gradlew.bat :app:assembleDebug --console=plain
```

Debug APK создаётся в `app/build/outputs/apk/debug/app-debug.apk`. Приложение можно запустить на выбранном устройстве из Android Studio.

Для проверки Android Auto нужен автомобильный хост или Desktop Head Unit (DHU) с соответствующей настройкой среды. Для проверки Bluetooth нужны реальные доступные устройства и необходимые разрешения Android. Запуск интерфейса на эмуляторе сам по себе не подтверждает доступ к автомобильным показаниям.

## Проверки

JVM-тесты покрывают состояния и жизненный цикл подписки на пробег, изоляцию подключений, автомобильные сессии, хранение JSONL, правила экспорта, Bluetooth-состояния, разрешения, UUID и контракты ViewModel.

```powershell
.\gradlew.bat :app:testDebugUnitTest --console=plain
.\gradlew.bat :app:assembleDebug :app:lintDebug --console=plain
```

Инструментальные тесты находятся в [`app/src/androidTest`](app/src/androidTest/). Для их запуска требуется подключённое устройство или подходящий эмулятор:

```powershell
.\gradlew.bat :app:connectedDebugAndroidTest --console=plain
```

Проверка на телефоне, Android Auto/DHU и физических Bluetooth-устройствах выполняется отдельно. Прохождение JVM-тестов не доказывает совместимость с конкретным автомобилем. Приведённые команды — инструкции запуска, а не утверждение о выполнении проверок на каждом устройстве.

## Ограничения и дальнейшее применение

- Наличие Android Auto или Bluetooth не гарантирует доступность общего одометра. Поддержка определяется автомобилем, хостом, устройством, разрешениями и фактическими ответами API.
- `Car ID` — ручная метка журнала, а не VIN, каталог модификаций или надёжно подтверждённая идентичность машины.
- Прототип не рассчитывает ТО, не ведёт продуктовую сервисную книжку, не записывает GPS-поездки и не подбирает запчасти.
- Настройки backup и проверки автомобильного хоста остаются частью экспериментальной конфигурации; готовность к публикации в магазине здесь не заявляется.

Результаты экспериментов и проверенные подходы будут использоваться при разработке отдельного CarCare. Его базовый сценарий — автомобиль и модификация, ручной пробег, регламент, персональный план ТО и история выполненных работ. Автоматические источники пробега добавляются по мере подтверждения их применимости.
